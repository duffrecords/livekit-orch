# Orchestrator API

HTTP API in front of LiveKit: start a session, stop it, dispatch an agent to a room, report
status. Code in `orchestrator/` (Python 3.13, FastAPI, `livekit-api` 1.2), manifest in
`charts/livekit-orch/templates/orchestrator.yaml`. Original plan: `plans/orchestrator-api.md`.

## Model

- **One session = one LiveKit room.** The session ID (`s-<10 hex>`) is the room name and is
  generated by the API. Rooms not named that way (e.g. made with `lk`) are not sessions.
- **LiveKit is the source of truth for live sessions.** The API persists nothing; the agent
  name and caller metadata are stored in the room's metadata. Restarting the orchestrator pod
  loses no live session (checked: sessions started before a restart were still listed after).
- **Ended sessions** are kept in memory (last 200, `ENDED_HISTORY_SIZE`). They are lost on
  restart and are per-process, so the Deployment runs one replica.
- Reached from the host at `http://localhost:8080` (kind maps `127.0.0.1:8080` → NodePort
  30080). Loopback only and unauthenticated: it mints room tokens, so it must not be on the LAN.

## Endpoints

| Method and path | Purpose |
|---|---|
| `POST /sessions` | Create the room and dispatch the agent in one LiveKit call; returns the session plus `url`, `token`, `identity`. Body (all optional): `agent` (default: first of `AGENT_NAMES`; `null` for no agent), `identity`, `metadata` |
| `GET /sessions` | Live sessions; `?include=ended` adds the in-memory history |
| `GET /sessions/{id}` | Status, participants, dispatches. 404 for an ID never seen |
| `DELETE /sessions/{id}` | Delete the room. 204, also when already ended; 404 if unknown |
| `POST /sessions/{id}/dispatches` | Dispatch another agent: `{"agent": "echo", "metadata": {…}}` |
| `POST /sessions/{id}/tokens` | Another join token: `{"identity": "user2"}` |
| `GET /workers` | Ready worker pods with their job count and load, read from each pod through the agent's headless Service (`WORKER_SERVICES`) |
| `GET /scaling/{agent}` | `{"agent", "sessions", "pending"}`: live sessions that need a worker for that agent. Read by the autoscaler |
| `POST /webhooks/livekit` | LiveKit webhook receiver; 401 unless signed with the API key |
| `GET /healthz`, `GET /readyz` | Liveness (process up) and readiness (LiveKit API answers within 2 s) |

OpenAPI schema and interactive docs are at `/openapi.json` and `/docs`. Unknown agent names
are a 422; LiveKit errors map to 502, an unreachable LiveKit to 503.

`make session`, `make sessions`, `make stop ID=…` wrap the common calls. `web/index.html`
has Start/Stop session buttons that use the API (`?start=1` starts one on load).

## Status

Derived on every read from `ListRooms`, `ListParticipants` and `ListDispatch`.

| Status | Meaning |
|---|---|
| `pending` | Room exists, an agent is expected, none is in the room. `pending_reason` says why: `no_workers`, `workers_full`, or `waiting` (a worker has room; the job is being assigned or is about to be dispatched again) |
| `ready` | Agent in the room, no user yet (or a session with no agent and no user) |
| `active` | At least one user in the room, and the agent if one is expected |
| `closing` | The agent has come and gone and the room is empty; it closes when `departure_timeout` expires |
| `ended` | Room gone. `end_reason`: `stopped` (DELETE), `expired` (reaper), LiveKit's reason from the webhook (`idle_timeout`, `api_delete`, …), or `unknown` (no webhook arrived) |

## Cleanup

| Trigger | Mechanism | Measured |
|---|---|---|
| `DELETE /sessions/{id}` | `DeleteRoom`; the worker's job process exits | Browser disconnected 0.14 s after the click |
| Nobody ever joins | Room `empty_timeout` (`EMPTY_TIMEOUT_SECONDS`, 120) | Closed at 120.3 s, `idle_timeout`. An agent in the room does not hold it open |
| Last user leaves or closes the tab | Echo agent ends its job; room `departure_timeout` (`DEPARTURE_TIMEOUT_SECONDS`, 10) | `ended` about 10 s after the tab closed, with no API call |
| Session too old | Reaper task every `REAPER_INTERVAL_SECONDS` (30) deletes sessions older than `SESSION_MAX_SECONDS` (1800), occupied or not | With the limit set to 60 s, two sessions with connected browsers ended as `expired` at 60 s |

`room_finished` webhooks record sessions that ended on their own, and every room and
participant event is logged.

A session left `pending` for more than `REDISPATCH_AFTER_SECONDS` (5) is dispatched again,
because LiveKit drops a dispatch no worker could take. This also replaces an agent that died
while a user was connected. Details: `docs/notes/scaling.md`.

## Logs

JSON lines on stdout (`make logs`): one `request` line per call (method, path, status,
duration, session ID; probes only at `DEBUG`), plus `session started`, `agent dispatched`,
`session ended` (reason and duration), `agent re-dispatched` and `livekit event` lines. Set `LOG_LEVEL` to change
the level.

## What LiveKit does (findings that shaped the code)

- `CreateRoom` with `agents=[…]` creates the room and the dispatch together; the agent joined
  within 0.5 s. Calling it again for an existing room returns that room and dispatches nothing.
- Dispatching to an agent name no worker has registered is accepted and waits forever. Hence
  the `AGENT_NAMES` allow-list. LiveKit has no public API to list registered workers.
- Dispatch job state is not a reliable signal: a job appeared about 4 s after its agent was in
  the room, and still read `running` after the agent had left. Agent presence comes from the
  participant list; job state is only used as evidence that an agent was once assigned.
- A room created with no agents still has one dispatch with an empty agent name (for
  automatically dispatched workers). It is ignored.
- `ListDispatch` on a missing room fails slowly with `unavailable`; `ListParticipants` returns
  an empty list. Existence is always checked with `ListRooms(names=[id])` first.
- A room disappears from `ListRooms` about 10 ms before its `room_finished` webhook arrives. A
  lookup in that gap waits up to 1 s for the webhook instead of answering 404.
- The webhook signing key can be set with `LIVEKIT_WEBHOOK_API_KEY` (from the existing Secret);
  `webhook.urls` has to be in the config file.
- With this client and server version the browser uses a single peer connection, so the test
  page's audio counters are under `publisher` and `subscriber` is null.
- While a pod is being replaced, the old one keeps receiving some requests for a few seconds.

## Verified (2026-09-30, macOS, headless Chrome with a fake microphone)

- `make test`: 26 unit tests against a fake LiveKit client (33 since the scaling milestone).
- `make smoke`: 10 sessions started in parallel, all `ready`, all stopped, no room left; 1.7 s
  in total on one worker pod. The worker afterwards held only its warm idle processes.
- Two browser tabs each started their own session from the test page and received echoed
  audio at the same time; stopping one left the other running.
- Readiness: with LiveKit scaled to 0 the orchestrator pod went NotReady and was not restarted.

## Limits and open points

- No authentication. Next step beyond a local demo: a shared bearer token.
- One replica (ended-session history and the reaper are in-process).
- A session whose agent crashes while a user is still connected reads `pending` (about 24 s
  after a hard kill, when LiveKit drops the dead participant) and gets a new agent from the
  re-dispatch.
- Worker capacity, warm processes and scaling are covered in `docs/notes/scaling.md`.
- An image rebuilt under the same `:dev` tag is picked up by the next `make deploy` (since the
  Helm milestone, `docs/notes/deployment.md`). For the workers, the rollout waits for live
  sessions to end.
