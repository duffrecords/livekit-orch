# Orchestrator API

> **Status: done.** Kept as the original plan. Differences in the result: a fifth status,
> `closing`; lookups wait briefly for the `room_finished` webhook instead of returning 404 in
> the gap after a room closes; the empty-name dispatch LiveKit adds to agent-less rooms is
> ignored; the image runs `uvicorn --factory app.main:create_app`. What was built and
> measured: `docs/notes/orchestrator.md`.

## Context

The networking spike left a working base: LiveKit v1.13.7 and one keyless `echo` worker on
kind, driven by hand with `lk token create` and `lk dispatch create`. This milestone replaces
those manual steps with the project's own HTTP API: start a session, stop it, dispatch an
agent to a room, and report status. It also covers the parts of "cleanup", "health checks"
and "basic logs" that belong to the API. Worker scaling, the real voice agent, Helm and the
README are later milestones.

**Outcome:** `curl -X POST localhost:8080/sessions` returns a URL and token, and
a client that joins with them finds the echo agent already in the room. `GET` shows the
session moving through its states, `DELETE` tears it down within a second, and abandoned
sessions clean themselves up.

## What LiveKit does (probed against the running cluster)

Checked with `livekit-api` 1.2.1 (the version the echo agent's lockfile already pins) against
server v1.13.7. These drive the design below.

| Probe | Result | Consequence |
|---|---|---|
| `CreateRoom` with `agents=[RoomAgentDispatch(agent_name="echo")]` | Room and dispatch are created in one call; the agent is in the room within 0.5 s | Start-session is one LiveKit call. This is the "create the room and dispatch as one step" the spike asked for |
| Dispatch job state after that | `dispatch.state.jobs` stayed empty for about 4 s while the agent was already an `ACTIVE` participant | Derive "agent joined" from participants of kind `AGENT`, not from job state |
| Dispatch to an agent name no worker registered | Accepted without error; the dispatch sits with no jobs indefinitely | Validate agent names against a configured list, and report a `pending` state |
| `CreateRoom` for a name that already exists | Returns the existing room; no second agent is dispatched | Session IDs are generated by the API, never taken from the caller |
| `DeleteRoom` | Room gone and agent job ended within 1 s. The echo agent logs three `ERROR` lines about closed data channels | Stop-session is one call. The log noise is expected |
| `DeleteRoom` on a missing room | `TwirpError` `not_found`, HTTP 404 | Map to 404 |
| `ListParticipants` on a missing room | Empty list, no error | Can't be used to test existence |
| `ListDispatch` on a missing room | `TwirpError` `unavailable`, HTTP 503 after a delay | Always check the room exists (`ListRooms(names=[id])`) first |
| Webhook signing key | `LIVEKIT_WEBHOOK_API_KEY` is accepted as an env var; `webhook.urls` is a list and must be in the config file | Key name comes from the existing Secret; the URL goes in the ConfigMap |

LiveKit has no public API for listing registered workers, so the API cannot tell "no worker
for this agent" from "workers are busy". Both show as `pending`.

## Design

| Piece | Choice | Why |
|---|---|---|
| Language / framework | Python 3.13, FastAPI + uvicorn, `livekit-api~=1.2`, managed with uv | Same toolchain and image pattern as `agents/echo`; `livekit-api` is async and already covers rooms, dispatch, tokens and webhook verification |
| Location | `orchestrator/` (own `pyproject.toml`, `uv.lock`, `Dockerfile`) | Separate image and dependency set from the agents |
| Session identity | One session = one LiveKit room. ID `s-<10 hex chars>`, generated server-side, used as the room name | No mapping table; avoids the duplicate-create case above |
| State | LiveKit is the source of truth for live sessions; nothing is persisted. Session attributes (agent, created-at) go in room metadata. Ended sessions are kept in a bounded in-memory list (last 200) | The API can restart without losing live sessions. Trade-off: history of ended sessions is lost on restart and is per-replica, so run one replica |
| Start | `CreateRoom(name, empty_timeout, departure_timeout, metadata, agents=[…])`, then mint a join token | Atomic room + dispatch |
| Stop | `DeleteRoom` | Ejects everyone; the worker's job subprocess exits |
| Automatic cleanup | `empty_timeout` 120 s (nobody ever joins), `departure_timeout` 10 s (last participant left), plus a reaper task that deletes rooms older than `SESSION_MAX_SECONDS` (default 1800) | Covers the abandoned-tab case, where a silent user would otherwise hold a worker slot forever |
| Lifecycle events | LiveKit webhooks → `POST /webhooks/livekit`, verified with `WebhookReceiver`. `room_finished` records the session as ended; `participant_joined` / `participant_left` / `room_started` are logged | Gives an `ended` state and an audit trail without polling. If a webhook is missed the session simply reads as 404 instead of `ended` |
| Agent names | Allow-list from `AGENT_NAMES` (default `echo`); anything else is a 422 | Unknown names are otherwise accepted silently by LiveKit |
| Exposure | Service `orchestrator` as NodePort 30080; kind maps host `127.0.0.1:8080` → 30080 | HTTP isn't sensitive to port remapping the way ICE is. Loopback only, unlike the LiveKit ports |
| Auth | None; the API is reachable from the host only | It mints room tokens, so it must not be on the LAN. A shared bearer token is the documented next step for anything beyond a local demo |
| CORS | Allow `http://localhost:8000` (configurable) | The test page is served from a different port |
| Health | `GET /healthz` (process up) for liveness; `GET /readyz` (a `ListRooms` call with a 2 s timeout) for readiness | Readiness should mean "can reach LiveKit", unlike the worker's `:8081` |
| Logs | JSON lines on stdout via stdlib `logging`: one per request (method, path, status, duration, session ID) and one per lifecycle event | Matches the worker's log format; no extra dependency |
| Packaging | Raw manifest `deploy/orchestrator.yaml` | Consistent with the spike; Helm comes with the scaling milestone |

### Endpoints

| Method and path | Purpose | Notes |
|---|---|---|
| `POST /sessions` | Start a session | Body: `{"agent": "echo", "identity": "user1", "metadata": {…}}`, all optional (`agent` defaults to the first allowed name; `"agent": null` creates a room with no agent). 201 with the session plus `url` and `token` |
| `GET /sessions` | List sessions | Live ones from `ListRooms`; `?include=ended` adds the in-memory history |
| `GET /sessions/{id}` | Session status | 404 if the ID was never seen or its history was lost |
| `DELETE /sessions/{id}` | Stop a session | 204; 404 if it doesn't exist. Already-ended is 204 |
| `POST /sessions/{id}/dispatches` | Dispatch an agent to the room | Body: `{"agent": "echo", "metadata": {…}}`. 201 with the dispatch. 404 if the session isn't live |
| `POST /sessions/{id}/tokens` | Mint another join token | Body: `{"identity": "user2"}`. For rejoining or a second participant |
| `POST /webhooks/livekit` | LiveKit webhook receiver | 401 on a bad signature |
| `GET /healthz`, `GET /readyz` | Probes | |

FastAPI serves the OpenAPI schema and `/docs` for free; link them from the README later.

### Session status

Derived on each read from one `ListRooms`, one `ListParticipants` and one `ListDispatch`.

| Status | Meaning |
|---|---|
| `pending` | Room exists, no agent participant yet (job not picked up: no worker, or workers at capacity) |
| `ready` | Agent is in the room, no user yet |
| `active` | Agent and at least one user are in the room |
| `closing` | Added during the build: the agent has come and gone and the room is empty, waiting out `departure_timeout`. Without it such a session read `pending` for about 10 s |
| `ended` | Room is gone; `end_reason` is `stopped` (DELETE), `expired` (reaper) or LiveKit's `room_end_reason` |

```json
{
  "id": "s-4f9c2a71be",
  "status": "active",
  "agent": "echo",
  "created_at": "2026-10-01T05:16:17Z",
  "participants": [
    {"identity": "agent-AJ_…", "kind": "agent", "state": "active"},
    {"identity": "user1", "kind": "standard", "state": "active"}
  ],
  "dispatches": [
    {"id": "AD_…", "agent": "echo", "jobs": [{"id": "AJ_…", "status": "running", "worker_id": "AW_…"}]}
  ]
}
```

`dispatches[].jobs` is passed through from LiveKit and can lag the participant list by a few
seconds. A session with `"agent": null` reports `ready`/`active` on users alone.

## Files

Create:

- `orchestrator/pyproject.toml`, `orchestrator/uv.lock`, `orchestrator/Dockerfile` (same shape as `agents/echo/Dockerfile`; `CMD uvicorn app.main:app --host 0.0.0.0 --port 8080`).
- `orchestrator/app/config.py`: settings from env (`LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, `LIVEKIT_PUBLIC_URL`, `AGENT_NAMES`, timeouts, `TOKEN_TTL_SECONDS`, `CORS_ORIGINS`).
- `orchestrator/app/sessions.py`: the LiveKit calls and status derivation. No FastAPI imports, so it is unit-testable with a fake client.
- `orchestrator/app/main.py`: app, routes, lifespan (one shared `LiveKitAPI`, reaper task), request-logging middleware, `TwirpError` → HTTP mapping.
- `orchestrator/app/logging.py`: JSON formatter.
- `orchestrator/tests/`: pytest for status derivation, validation and error mapping against a fake LiveKit client.
- `deploy/orchestrator.yaml`: Deployment (1 replica, `imagePullPolicy: Never`, `enableServiceLinks: false`, env from Secret `livekit-keys`, `LIVEKIT_URL=http://livekit.livekit.svc.cluster.local:7880`, probes) and NodePort Service.
- `scripts/smoke.sh`: the end-to-end check in "Verification" below, using only `curl` and `jq`.

Change:

- `kind-config.yaml`: add the `30080 → 127.0.0.1:8080` TCP mapping. **kind can't add port mappings to a live cluster, so this needs `make down && make up`.**
- `deploy/livekit.yaml`: add `webhook.urls: [http://orchestrator.livekit.svc.cluster.local:8080/webhooks/livekit]` to the ConfigMap and `LIVEKIT_WEBHOOK_API_KEY` (from Secret `livekit-keys`) to the pod env.
- `Makefile`: build and load both images; wait for the orchestrator rollout; add `session`, `sessions`, `stop`, `smoke` and `test` targets; include the orchestrator in `logs`. `token` and `dispatch` stay as low-level debugging tools.
- `.env.example`: no new secrets. `LIVEKIT_PUBLIC_URL` defaults to `ws://localhost:7880` in the manifest.
- `web/index.html`: add "Start session" and "Stop session" buttons that call the API and connect with the returned URL and token. The manual URL/token fields stay.

## Steps and pass criteria

1. **Skeleton and health.** App, config, JSON logging, `/healthz`, `/readyz`, image, manifest, kind mapping, Makefile. Pass: after `make down && make up`, `curl localhost:8080/readyz` is 200; scaling LiveKit to 0 turns the orchestrator pod NotReady while it stays alive.
2. **Start, status, stop.** `POST /sessions`, `GET /sessions[/id]`, `DELETE /sessions/{id}`. Pass: POST returns in under a second with a token; GET shows `ready` within 2 s; joining from the test page with the returned token gives `active` and an audible echo; DELETE disconnects the browser and the worker log shows the job ending; a second DELETE is 204, an unknown ID is 404, an unknown agent is 422.
3. **Dispatch and tokens.** `POST /sessions/{id}/dispatches` and `/tokens`. Pass: a session started with `"agent": null` gains an echo agent after a dispatch call; a second token lets a second tab join the same room.
4. **Webhooks and cleanup.** Webhook receiver, ended-session history, timeouts, reaper. Pass: closing the browser tab ends the session about 10 s later with no API call, and GET then reports `ended` with a reason; a session nobody joins ends after `empty_timeout`; with `SESSION_MAX_SECONDS=60` an occupied session is reaped; a webhook with a bad signature gets 401.
5. **Concurrency.** Pass: `scripts/smoke.sh` starts 10 sessions in parallel, sees 10 distinct rooms each reach `ready`, deletes them, and ends with `lk room list` empty and no leftover job processes in the worker pod.
6. **Test page.** Pass: two browser tabs each start their own session from the page and echo independently; "Stop session" in one leaves the other running.
7. **Wrap-up.** Update `CLAUDE.md` ("Decisions so far", next milestone) and add an orchestrator section to `docs/notes/`. No commits unless you ask.

Before writing step 4, confirm the webhook payload fields (`event`, `room`, `room_end_reason`)
against a real delivery, per the project rule on API drift: the field list was read from the
package, not from a received event.

## Risks and open points

- **Cluster recreation.** Step 1 destroys the running cluster. `kubectl port-forward` would avoid that but dies whenever the pod restarts, so it is a poor fit for a demo.
- **One worker pod's capacity is unknown.** Step 5 may show sessions stuck in `pending` if 10 jobs exceed the worker's load threshold. That is a finding for the scaling milestone, not a failure of this one; lower the count and record the number.
- **`--dev` still prints join tokens in the LiveKit log.** Unchanged here; it goes away with the Helm chart.
- **Single replica.** Ended-session history and the reaper assume one orchestrator pod. Live-session calls are stateless and would work with more.
